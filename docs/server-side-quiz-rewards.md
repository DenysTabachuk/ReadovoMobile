# TODO: перенести нарахування винагород за квізи на бекенд

Статус: заплановано. Ця задача стосується квізів статей, vocabulary-квізів і словникових тестів.

## Поточна проблема

Фронтенд викликає `calculateQuizReward`, додає результат до отриманого балансу й надсилає
нові значення `balance` та `testsCompleted` через
`PATCH /achievements/profile/:userId/progress`.

Бекенд перевіряє числові межі цих полів, але не перевіряє результат квізу та не розраховує
його винагороду. Через це клієнт може підмінити баланс або кількість завершених тестів.
Паралельні запити можуть перезаписувати баланс застарілим значенням, а повторне завершення
не має прив'язки нарахування до унікальної серверної сесії квізу.

## Бажана поведінка

Фронтенд надсилає ідентифікатор сесії та відповіді користувача. Бекенд перевіряє їх,
визначає результат, розраховує винагороду й нараховує її один раз за сесію.
Фронтенд показує результат, який повернув сервер.

Запропонований контракт для погодження:

```http
POST /quiz-sessions/:sessionId/complete
```

```json
{
  "answers": [{ "questionId": "question-1", "selectedOptionIds": ["option-2"] }]
}
```

Приклад відповіді:

```json
{
  "sessionId": "session-123",
  "correctAnswers": 8,
  "totalQuestions": 10,
  "percentage": 80,
  "rewardCoins": 26,
  "balance": 146,
  "testsCompleted": 4
}
```

Це приклад майбутнього контракту, а не вже реалізований endpoint. Остаточний шлях і формат
потрібно узгодити з поточними API квізів і словника. Перевірити відповідність поля
`answers` усім підтримуваним типам запитань, зокрема множинному вибору.

## Бекенд

- [ ] Створювати й зберігати серверну сесію квізу: власник, тип, запитання, правильні
      відповіді, рівень, довжина тексту та стан завершення. Клієнт не повинен визначати
      правильність власних відповідей або параметри винагороди.
- [ ] Визначати користувача з авторизованої сесії та перевіряти право завершити цей квіз.
- [ ] Валідувати відповіді: ідентифікатори запитань і варіантів, повтори, пропущені
      відповіді та обмеження конкретного типу запитання.
- [ ] Перенести формулу та правила бонусів із `calculateQuizReward` на сервер.
      На першому етапі зберегти чинні суми й пороги, якщо окремо не погоджено зміну правил.
- [ ] Визначати бонус першого тесту за серверними даними й захистити його від одночасного
      отримання в різних сесіях одного користувача.
- [ ] У транзакції зберігати завершення сесії, суму винагороди, атомарний приріст балансу
      та лічильника тестів. Захистити завершення унікальним обмеженням або умовним записом.
- [ ] Повторний запит завершення тієї самої сесії має повертати збережений результат
      без повторного нарахування, зокрема при одночасних запитах і повторі після таймауту.
- [ ] Прив'язати до перевіреного завершення оновлення досягнень і streak. Повторний запит
      не має повторно запускати побічні ефекти. Узгодити формат їх повернення клієнту.
- [ ] Закрити можливість довільно змінювати `balance` і `testsCompleted` через старий
      progress endpoint; перевірити інші поля прогресу й усі місця зміни балансу.
- [ ] Повертати актуальний баланс після всіх пов'язаних бонусів. Задокументувати, що саме
      включає `rewardCoins`, щоб UI не плутав винагороду квізу з бонусами досягнень.

      Якщо залишиться попередній розрахунок для UI, позначити його як оцінку,
      яка не використовується для зміни балансу.

## Тести та перехід

- [ ] Серверні тести формули: усі пороги точності, рівні, довжини, округлення й бонуси.
- [ ] Інтеграційні тести чужої/невідомої сесії, некоректних відповідей і підміни винагороди.
- [ ] Тести повторного завершення та паралельних запитів, включно з двома різними сесіями
      одного користувача: баланс не втрачає приростів, перший бонус надається один раз.
- [ ] Тести відкату транзакції та відновлення після невдалої відповіді клієнту.

- [ ] Узгодити випуск сервера й мобільного клієнта. Старий endpoint не повинен залишатися
      способом довільної зміни балансу; явно визначити підтримку старих версій застосунку.
